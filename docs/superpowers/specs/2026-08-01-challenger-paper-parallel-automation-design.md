# Challenger 与 System Paper 并行自动化设计

日期：2026-08-01

状态：冻结

来源会话：`019fb7ae-af38-7b73-97da-97a30bb7e7b1`

## 1. 目标与裁决

目标流程固定为：

```text
现在完善并冻结系统
        ↓
尽量同一天启动
├─ Challenger 540 槽位继续自然收集
└─ System Paper 实时模拟运行
        ↓
分别完成各自 90 天验收
        ↓
全部通过后才考虑极小资金 Canary
```

“同一天启动”是运营目标，不是允许降低安全门槛的授权。Challenger 已经开始并必须
保持原时间线不变；System Paper 只有在系统、策略、参数、成本、模拟成交和风险配置
冻结，且启动验收通过后才能形成自己的起始凭证。如果无法在同一天满足这些条件，
Challenger 继续自然运行，System Paper 从后来真实合格的启动时刻独立计算 90 个自然日。
不得回填、借用 Challenger 的既有天数或修改时间戳制造同日启动。

## 2. 两条独立证据流

### 2.1 Challenger confirmatory cohort

- 保留既有冻结计划、540 个连续 4h 槽位和固定 tail end；
- 每日自然 Runner 与 08:10 evidence maintenance 的职责、时间和权限不变；
- 08:25 自动化只做只读连续性验收，不触发 Runner、maintenance、补槽或回填；
- tail end 前只报告健康、槽位数、Episode 数与下个要求槽位，不读取或传播
  confirmatory PnL，不形成提前 PASS；
- 固定尾部后的累计评估仍由冻结 evaluator 对完整证据执行一次。

### 2.2 System Paper

System Paper 是系统级实时模拟，不是 Challenger 的别名，也不能替代 Challenger。
它必须使用实时公开市场输入和模拟 Broker，覆盖：

- 信号到订单的完整状态机；
- 接受、拒绝、取消、部分成交、超时和 UNKNOWN；
- 保守费用、滑点、Funding 和可成交性假设；
- 仓位、PnL、风险锁、限额和 kill switch；
- 断线恢复、幂等重试、重启恢复、账本与持仓对账；
- 所有信号、被拒订单、亏损交易和故障的只追加记录；
- 心跳、延迟、数据缺口、异常状态和人工介入告警。

Paper 不得持有交易 API 权限，不得访问余额或真实 Broker，不得创建、取消或修改真实
订单。允许的网络边界仅限在冻结合约中明确列出的公开市场读取；任何账户成本读取若
仍需要凭据，必须先另行完成最小权限、只读、一次性取证设计和验收，不能被日常自动化
静默开启。

## 3. System Paper 启动门

开始 90 天计时前必须同时满足：

1. 冻结策略版本、参数、标的、方向、周期、资本基准和风险限额；
2. 冻结市场数据来源、时钟、缺口规则、费用、滑点、Funding 和 fill model；
3. 模拟 Broker、订单生命周期、账本、持仓和对账路径通过测试；
4. 重启恢复、重复消息、乱序、超时、部分成交、断网和磁盘故障注入通过；
5. 运行根目录 owner-only、只追加、no-overwrite，外部 attestation 可重放；
6. LaunchAgent/调度合同、执行快照、安装凭证和首次自然槽凭证全部验证；
7. `production_activation.enabled=false`，无交易凭据、无真实订单权限；
8. 发布唯一、不可变的 Paper start receipt，绑定上述全部哈希和实际起始时间。

启动前的 smoke、历史重放、失败运行或工程调试不计入 90 天。任何影响策略、模型、
参数、风险、成本、fill 或统计判断的实质变更都创建新的 evidence scope 和起始凭证，
旧版本证据保留但不得拼接。仅修复不改变语义的观测/告警缺陷，也必须由冻结变更分类器
明确判定后才能保持原 cohort。

## 4. 完整 V1 工程的依赖化并行

本自动化负责协调完整 V1 工程，不只负责等待两个 90 天窗口。工程采用依赖图推进，
而不是“所有模块同时修改”：互不共享可变状态的工作流可以并行；策略、执行、账本、
风险和运行安装等关键链必须按门槛串行。这样可以在等待自然证据时完成大量工程，又不让
Web 或外围功能污染交易核心。

### 4.1 现在可以并行完成的工程流

1. **Paper 核心关键路径**：模拟 Broker、订单状态机、成交模型、费用/Funding、
   双分录账本、持仓、对账、风险锁、恢复和最终评估器；
2. **数据与证据**：公开实时数据接入、时钟和缺口治理、来源 bundle、只追加 artifact、
   production loader、外部 attestation 和完整性检查；
3. **可靠性与安全**：故障注入、幂等、重启恢复、权限、secret absence、审计、备份与
   恢复演练；
4. **可观测性与运维**：结构化日志、指标、健康状态、告警规则、runbook、启动/停止/
   升级/回滚流程；
5. **只读 Web 控制台**：项目总览、Challenger/Paper 独立时间线、槽位与证据健康、
   模拟仓位/订单/账本、风险状态、告警、版本与验收门；
6. **交付工程**：Schema、契约、测试、CI、构建清单、SBOM/依赖许可证、文档、ADR、
   版本和 GitHub 发布流程。

上述“并行”表示规划和实现可以交错进行，不表示可以绕过共同接口冻结。每条工作流先
定义输入/输出 Schema 和不可变接口，再在隔离分支中实现；合并前运行聚焦、相邻和全量
回归。任何与当前自然 Challenger 运行文件重叠的变更必须延后或证明无副作用。

### 4.2 Web 的边界

当前仓库没有 Web/API 实现，因此 Web 是新增工作流，不应被误判为“已经接近完成”。
第一版固定为本机只读观察面：

- 后端只读取经 loader 验证的 projection/read model，不直接读取或修改交易状态库；
- 前端不提供下单、改参数、补槽、重跑、启动/停止服务或清除告警按钮；
- 页面显示证据状态与来源时间，区分 runtime、research、Paper 和 release 资格；
- confirmatory tail 前不展示被禁止的 Challenger 收益字段；
- 默认只绑定 loopback，不公开部署；远程访问、身份认证和公网托管另设安全设计门；
- Web 故障不得阻止 Runner/Paper，也不得改变账本、风控或证据；核心运行故障必须能在
  没有 Web 的情况下被 CLI、日志和告警发现。

Web 可以与 Paper 核心并行建设，但不位于 Paper 启动的最短关键路径。若 Web 尚未完成，
只要 CLI/日志/告警已达到运行验收标准，不应人为推迟安全合格的 Paper；反之，漂亮的
Dashboard 不能补偿模拟 Broker、对账、成本或风险门缺失。

### 4.3 明确延后的事项

下列事项不因“先把所有事情做完”而获得授权：

- 真实交易 API key、余额权限、Broker 接入和任何真钱订单；
- 公网 Web 部署、第三方账户系统、付费功能或面向外部用户运营；
- LLM/Agent/强化学习直接决策或下单；
- 为追求功能数量扩大 V1 标的、交易所、杠杆、频率或策略族；
- 未经独立设计和安全验收的 Canary 自动化。

这些内容会增加攻击面或改变研究 scope，提前实现反而延长可靠盈利证据的关键路径。

## 5. 新账号下的单一每日自动化

旧账号自动化 `challenger` 应在新账号中更新为一个 phase-aware heartbeat，并绑定当前
项目任务，避免同一线程或同一机器存在两个重复协调器。固定每天北京时间 08:25 运行
一次，不做高频轮询。

自动化按状态执行：

### Phase A：V1 engineering 与 Paper readiness

- 先只读检查 Challenger 自然运行与 maintenance 证据；
- 对照本设计和现有路线图维护全局依赖图，优先识别 System Paper 的最前置未完成门；
- 关键路径每次推进一个有界、可验证的工程批次；独立 Web、文档、可靠性或可观测性
  工作可以并行，但不得共享未冻结接口或触碰自然运行状态；
- 设计、测试、实现、验证、PR、main 和 tag 遵守仓库既有流程；
- 不因赶同日起点而跳过测试、冻结或启动验收。

### Phase B：Paper launch acceptance

- 所有工程门通过后，冻结 Paper release candidate；
- 先做无副作用预检，再安装独立 Paper 调度；
- 不触发 Challenger Runner 或 Challenger maintenance；
- 仅首次自然 Paper 槽成功后发布 start receipt 并开始计时；
- 启动失败则保存失败证据，禁止补槽或伪造成功。

### Phase C：Dual monitoring

- Challenger：继续 tail-blind 只读连续性验收；
- Paper：只读核验计划槽、实时公开输入、模拟订单、账本、对账、风险和告警连续性；
- 两条流分别报告起点、自然天数、槽位、缺口、故障和下一门槛；
- 日常健康运行不制造 Git commit、PR、tag 或版本号；
- 仅实质代码/设计变更、不可变启动凭证、失败证据规范或最终结果进入版本流程。

### Phase D：Independent final gates

- Challenger 只在其冻结 tail end 后执行自己的最终门；
- Paper 只在其 start receipt 派生的完整 90 个自然日后执行自己的最终门；
- FAIL 或 INCONCLUSIVE 必须如实保留，禁止改阈值、挑样本或重跑寻找更好结果；
- 两者全部 PASS 也只形成“可以设计极小资金 Canary”的资格，不自动安装、不自动入金、
  不自动创建 API key，也不自动下单。

## 6. 失败关闭与人工边界

出现下列任一情况，自动化停止当前推进并转入取证：

- 槽位、日志、bundle、receipt、archive、result 或索引不连续；
- Git 基线、tag、artifact、loader、LaunchAgent 或权限与冻结值不一致；
- 市场请求超出 allowlist，出现账户/Broker/订单调用，或 production activation 被打开；
- Paper 与 Challenger 状态、目录、服务名或凭证发生交叉污染；
- 关键统计或经济字段缺失、不可重放、被覆盖或被人工输入；
- 自动化无法确认自己绑定的是目标私有仓库、新账号当前任务和唯一 heartbeat。

自动化可以在既有授权范围内完成代码、测试和 GitHub 交付，但任何真实资金、交易凭据、
交易权限、Canary 安装或对外不可逆操作都不属于本设计授权。

## 7. 调度迁移验收

- 新账号中只存在一个 active heartbeat；
- automation id 保持 `challenger`，固定每天北京时间 08:25；
- target thread 绑定新账号当前项目任务，不再指向旧任务；
- prompt 同时包含两条独立证据流、四阶段状态机和失败关闭边界；
- 调度更新本身不运行 Runner、maintenance、Paper、网络请求或 Git 发布；
- 更新后重新读取自动化，逐项核对 id、状态、时间、目标任务和完整 prompt；
- 若旧账号仍可能独立运行同名 heartbeat，应将其视为外部重复调度风险：新自动化不得
  假设自己能跨账号删除旧任务，首次运行必须检查并报告同机重复副作用迹象。

## 8. 对赚钱目标的意义

并行安排减少了“先等 Challenger 90 天、再从零开始等 Paper 90 天”的串行等待，
但没有把等待变成收益证明。Challenger回答固定策略研究信号是否值得继续，System Paper
回答完整系统在实时输入、成本、模拟成交和故障条件下是否可运行；两者都通过后，仍只能
考虑受限的极小资金 Canary。赚钱目标最终依赖成本后、风险调整后、可复现的真实证据，
而不是 AI 标签、回测峰值或提前读取的中期结果。
