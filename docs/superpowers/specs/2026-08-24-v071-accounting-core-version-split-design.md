# v0.71 Accounting Core Version Split Design

## 1. Decision

The approved v0.71 plan required a semantic split when its exact six-module
budget could not contain Tasks 5 and 6.  At the approved Task 4 checkpoint the
six modules contain 2,042 physical lines; subtracting the frozen v0.70 baseline
of 843 yields 1,199 of the allowed 1,200 lines.  Task 5 therefore cannot begin
inside v0.71.

v0.71 is narrowed to the already reviewed deterministic fixture input,
decision, signed accounting, position snapshot, funding, and risk-transition
core.  v0.72 will be separately preregistered for order/fill/stop/reconciliation
lifecycle, v2 opportunity-log integration, crash recovery, and complete-cycle
goldens.  No implementation is moved by deleting tests or safety validation.

This document supersedes Sections 14 and 16 and Tasks 5–8 of
`2026-08-24-binance-deterministic-simulation-design.md` and its implementation
plan only where those sections assign post-Task-4 work to v0.71.  All safety,
determinism, accounting, risk, provenance, and non-authority requirements remain
unchanged.

## 2. Alternatives rejected

1. Compress Tasks 5–6 into the final line. Rejected because it would force
   deletion or concealment of lifecycle, recovery, and reconciliation logic.
2. Raise or redefine the approved budget after implementation evidence was
   observed. Rejected as a post-hoc governance change.
3. Discard the reviewed accounting core. Rejected because Tasks 1–4 are a
   coherent, independently testable boundary and discarding them adds no safety.

## 3. Exact v0.71 boundary

v0.71 contains:

- the immutable credential-free simulation contract builder and strict schema;
- strict canonical Binance fixture-input parsing with exact plan, contract,
  build, opportunity, instrument, quote, bar, and funding bindings;
- deterministic LONG/SHORT/FLAT decisions bound to plan and policy hashes;
- verified-flat genesis and parent/self-hashed signed-position snapshots;
- conservative fill prices, maximum legal-lot sizing, multiplier, fee, funding,
  cash, isolated-margin, realized/unrealized PnL, equity, and exposure equations;
- daily-loss, drawdown, margin-exhaustion, gross-drift, projected-risk,
  no-trade, unresolved-position, and enforcement of an already-supplied
  economic-gap lock in pure snapshots; canonical MISSED derivation is v0.72;
- exactly one formal contract artifact generated by the reviewed builder;
- tests and release evidence for this boundary.

v0.71 explicitly does not contain or claim:

- order attempts, acknowledgements, partial fills, UNKNOWN resolution, stop
  lifecycle, venue reconciliation, or duplicate economic-order prevention;
- v2 result evidence, event-log orchestration, fixture runner, crash recovery,
  concurrency, complete-cycle result goldens, observer, evaluator, install, or
  start receipt;
- network, account, credential, Broker, exchange-order, production-root, funds,
  Paper completion, profitability, Canary, or live-trading authority.

The release status is exactly
`FIXTURE_ACCOUNTING_CORE_VERIFIED_LIFECYCLE_NOT_IMPLEMENTED`.  It is evidence
that the bounded pure core passed its gates, not that System Paper or a trading
engine is operational.

## 4. v0.71 formal artifact

The sole new formal artifact is
`artifacts/challenger-replacement/challenger-replacement-binance-simulation-contract-v0.71.0.json`.
Its bytes must be canonical output from
`build_challenger_replacement_simulation_contract(plan=exact_v0_69_plan)` and
must replay through the strict loader.  A pre-artifact regression must fail for
the missing exact path before bytes are added.  The artifact contains no future
commit, tag, CI, runtime, account, or authority identity.

No golden fixture manifest or portable result artifact is allowed in v0.71:
the complete lifecycle and v2 result schema do not yet exist.  Unit-test fixture
builders remain test-only and non-authoritative.

## 5. Release and verification gates

The final v0.71 code state must pass:

1. focused accounting, input, contract, decision, instrument, and order-adjacent
   tests;
2. the complete local suite once, compileall, `make validate`, and diff checks;
3. exact contract-artifact replay and release metadata tests;
4. six-module `(current total - 843) <= 1200`, each module `<= 700`, and no
   unrelated production deletion credited to the budget;
5. one independent complete review with Critical and Important findings at zero;
6. public Draft PR Python 3.9/3.12 and macOS arm64 CI, merged-main CI, and an
   annotated `v0.71.0` whose peeled commit equals `origin/main`.

Release documents must state the exact Task 4 test/review evidence and the
remaining v0.72 work.  They must not claim unexecuted CI before it runs.

## 6. v0.72 handoff invariant

The original downstream numbering is explicitly superseded: v0.72 is the
lifecycle, v2 result, canonical event-log integration, crash recovery, and
complete-cycle golden version; v0.73 is the earliest evaluator, strict observer,
and v0.61 UI-wiring version; deployment/start work moves to v0.74 or the next
available separately frozen versions. No original requirement is dropped.

v0.72 starts from the released v0.71 tag and receives a new design, plan, line
budget, TDD cycles, review, and release. It may consume the public pure-core
interfaces but may not rewrite v0.71 artifacts, tests, release identity, or
observed results. The canonical event log remains the sole future authority;
exports and snapshots remain projections. No service installation or start is
authorized by either version.
